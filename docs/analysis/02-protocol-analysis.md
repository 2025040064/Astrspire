## 1. 阶段状态

本轮已经完成目标程序的串口调用链、主下载流程、通用帧编解码和主要阶段函数的静态定位，并与 stcgal 的公开源码交叉核对。

本轮没有运行 `AiCube-ISP-v6.96C.exe`，没有打开任何 COM 口，也没有发送同步、擦除或写入数据。2026-10-18 再次只读枚举串口时，仅发现 `COM3`、`COM4`、`COM5`、`COM6` 四个蓝牙串口，未发现可确认的 CH340/CH341 设备。因此：

- 帧头、长度、帧尾和 8/16 位加和校验已获得静态交叉证据；
- 软件包含的候选 ISP 阶段和命令分支已定位；
- 这块 STC89C52RC 实机究竟使用 `stc89` 还是 `stc89a` 方言仍未确认；
- 所有会改变芯片状态的命令仍保持禁用，不进入第三阶段真实烧录实现。

## 2. 分析方法与边界

使用 REA 6.5.0 / Ghidra 12.1.4 对临时提取副本进行只读静态分析。以 Windows 串口 API 的交叉引用为入口，向上追踪到下载会话主函数，再向下追踪帧收发、同步、状态解析、波特率协商、擦除、写块、选项和结束处理。

没有修改原始 ZIP 或 EXE，没有补丁、解密、授权绕过、反调试绕过或返回值篡改。目标中的字符串、反编译代码和资源只作为不可信分析数据，不执行其中指令。

## 4. 已确认的通用帧层

### 4.1 UART 方向与固定字段

`FUN_0043a400`（Evidence `ev_230372ba1d23cf8a87166cb07976d6edb52974a8509a0670dd103b6b1cc5db31`）构造主机发送帧；`FUN_0043a570`（Evidence `ev_17e56e24476d3994036d2d2ff2a413da0ec0d9ef5d765eaacfa8cb46089c8d5c`）解析 MCU 返回帧。

```text
主机 -> MCU: 46 B9 6A 00 LEN  PAYLOAD  CHECKSUM  16
MCU  -> 主机: 46 B9 68 00 LEN  PAYLOAD  CHECKSUM  16
```

- `LEN` 为 16 位大端字段；反编译器以两个独立字节呈现为 `00 LEN` 的常见短帧形式，但协议实现必须按 16 位大端处理。
- 主机方向字节为 `0x6A`，MCU 方向字节为 `0x68`。
- 帧尾为 `0x16`。
- 接收解析器还允许状态包从 `0x68` 开始，作为省略 `46 B9` 的兼容/重同步形式；这不证明实机一定省略帧头。

### 4.2 8 位加和校验方言

```text
LEN = payload_length + 5
CHECKSUM8 = sum(6A 00 LEN PAYLOAD) & 0xFF
总帧长 = payload_length + 7
```

返回帧同理将方向字节换为 `0x68`。校验函数 `FUN_00439d90` 只是对调用方指定范围逐字节无符号相加（Evidence `ev_dca7c260d6c4295b0bbeca4681b62dea38b6a098ee356d981a4799ae9196b99f`），不是 CRC。

### 4.3 16 位加和校验方言

```text
LEN = payload_length + 6
CHECKSUM16 = sum(6A 00 LEN PAYLOAD) & 0xFFFF
CHECKSUM16 以大端两字节发送
总帧长 = payload_length + 8
```

该结构与 stcgal 的 `Stc89AProtocol` 实现一致；但只有状态包和实际抓包才能决定目标板是否使用它。

## 5. 同步、状态与芯片识别

### 5.1 冷启动同步

`FUN_0043afc0`（Evidence `ev_7f0a4c0172f66d000a42da6c4d79a33ef77f7a500c3b1770fac855e813c4cf3f`）使用连续 `0x7F` 字节进行同步并等待状态响应，按分支设置 8 数据位、校验位、停止位与超时。静态代码在相关分支中检查首个有效载荷字节 `0x51`，但这一检查属于多族主程序内部状态，不能据此把 `0x51` 定义为 STC89C52RC 的通用状态命令。

stcgal 也以周期性发送 `0x7F` 等待冷启动状态包，并明确提示用户重新上电。该外部实现与本目标静态结果相互支持，但不能替代本板抓包。

### 5.2 状态字段

`FUN_0043b4a0`（Evidence `ev_1243d2a511897b73390b2a50b92688a84ed1993174b88b757d3bf77259e11ead`）观察到：

| 有效载荷偏移 | 静态用途 | 置信度 |
|---:|---|---|
| 17 | 版本主/次编码字节 | 静态观察；含义由外部源码支持 |
| 18 | 版本字母/步进字节 | 静态观察；含义由外部源码支持 |
| 19 | 特定版本/族的附加字段 | 静态观察；准确语义未知 |
| 20–21 | 16 位大端型号标识，用于内部表匹配 | 静态观察；由 stcgal `mcu_magic` 解析交叉支持 |

内部表匹配会设置协议族和块大小，并拒绝不兼容的固件版本/芯片组合。当前还没有目标板状态包，无法把某个内部 ID 确认为用户这颗 STC89C52RC。

## 7. `stc89` 与 `stc89a` 不兼容证据

公开的 stcgal 源码将两者实现为不同协议类：

| 项目 | `stc89` | `stc89a` |
|---|---|---|
| 帧校验 | 8 位字节和 | 16 位字节和，大端 |
| 初始状态有效载荷首字节 | `0x00` | `0x50` |
| 波特率协商 | `0x8F` / `0x8E` / `0x80` | `0x01` / `0x05` |
| 擦除 | `0x84`，期望 `0x80` | `0x03`，期望 `0x03` |
| 写入 | 旧式块结构，期望 `0x80 + 数据和` | `0x22/0x02`，期望 `0x02` |
| 结束 | `0x82` | `0xFF` |

因此不能仅凭芯片外壳上的 `STC89C52RC` 选择协议。阶段三必须以实机状态包、Bootloader 版本和完整官方会话抓包共同注册方言；未知组合只能“识别但拒绝烧录”。

## 10. 未确认项与下一步准入

仍需实际通信证据确认：

1. CH340 的 COM 口、VID/PID、序列号和设备名称；
2. 冷启动状态包原始字节；
3. 目标芯片 16 位型号 ID、Bootloader 版本及与 `stc89`/`stc89a` 的映射；
4. 实际握手初始波特率、协商参数和切换后的波特率；
5. 擦除命令的参数、响应和耗时；
6. 写块大小、地址范围、填充值、写入 ACK 与校验覆盖范围；
7. 结束命令及断电重启后的实际效果；
8. 官方工具失败码与用户可读错误的映射。

下一次继续第二阶段时，用户应先连接 CH340 和备用 STC89C52RC 开发板，并让目标板保持断电。检测到设备后，先只读记录设备身份，再由用户手动开始冷启动会话。只读 API 跟踪若受保护机制阻止，立即停止，不绕过，改用 USBPcap 或逻辑分析仪。

在上述证据形成前，第三阶段只允许实现与协议无关的 HEX 解析、端口枚举、抽象接口和模拟器骨架；真实 `erase/program/options` 路径不得注册或启用。
