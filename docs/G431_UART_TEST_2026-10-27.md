# G431 UART 测试与串口诊断改进

## 范围

测试目标为 STM32G431RBT6；真实 UART，不以 SWD 内存采集代替。保留 dev3 旧产物，不修改用户原工程、不操作 STC、不解除保护。

本轮使用本机 STM32Cube G4 v1.6.3 HAL 与 GCC 构建独立测试程序。固件只操作 USART1 的 PA9/PA10、系统节拍和自有 RAM，不执行 Flash、EEPROM 或选项字节写入。设备程序替换仍须在确认探针、芯片身份和保护状态后，双份完整备份、比对哈希；实验结束恢复并完整回读。构建成功不是实板验收。

## 已实现的软件改进

- 端口打开时显示“等待接收数据”，不把打开成功表述为目标通信成功。
- 三秒无数据提示检查目标程序、TX/RX、GND 和波特率；保持连接，不自动重连或发命令。
- FireWater/JustFloat 持续有字节但无有效采样时提示格式不匹配；恢复后更新为接收状态。
- RawData 不要求数值采样；FireWater 普通文本保持文本，不误计为解析错误。
- 新增独立接收统计：字节、数值帧、解析错误；TX 已交驱动仍不代表设备确认。
- 所有原始数据继续进入原接收与记录链路，不为诊断丢弃数据。

## 独立测试固件

源码：`firmware/g431_uart/main.c`，HAL 配置同目录。构建：

```powershell
.\.venv\Scripts\python.exe tools\build_g431_uart_firmware.py
```

产物：`build-preview/runtime-g431-uart-20261027/firmware/g431_uart.hex`、`.bin`、`.elf` 及 `manifest.json`。Flash/RAM 链接限制复用本项目 32KiB/16KiB 保守实验布局；不是容量自动探测。供应商 HAL/CMSIS 只作为本机只读构建输入。

接线（3.3V UART）：PA9 TX → 转换器 RX，PA10 RX → 转换器 TX，GND 共地。串口为 115200、8N1。DAP 是否支持 UART 取决于实际型号与虚拟串口枚举；只连接 SWD 不能充当 UART。

启动默认不发数据，命令使用 LF 或 CRLF 结尾：

| 自有命令 | 行为 |
|---|---|
| `ASTR:HELLO` | 停止状态返回 `ASTRSPIRE:G431_UART_V1,115200,16,10` |
| `ASTR:PING:<token>` | 停止状态返回 `PONG:<token>`；用于双向链路确认 |
| `ASTR:START` | 开始 JustFloat 16 通道、100帧/秒，不混入文本 ACK |
| `ASTR:STOP` | 停止发送，不复位、不改写配置 |

通道1为设备序号，通道2为板端毫秒；通道3–15为由序号计算的斜坡信号，通道16为 RX 异常计数，正常应为零。每帧68字节，含4字节 JustFloat 帧尾；约6800字节/秒，占115200/8N1理论线速约59%。这些是测试信号，不是 ADC 电压。

## 验收工具

`tools/g431_uart_acceptance.py` 是独立、显式的硬件工具，普通测试不调用它。必须先完成备份并安装本轮固件。COM、VID/PID 按当前枚举填写，不能照抄历史端口：

```powershell
.\.venv\Scripts\python.exe tools\g431_uart_acceptance.py --port COM8 --vid 1A86 --pid 7523 --fixture-installed --seconds 60 --output build-preview\runtime-g431-uart-20261027\live-60s
```

先 HELLO 精确匹配，再随机 token 往返确认，之后通过实际 SerialLinkWorker 发送 START、接收 JustFloat，并使用 AsyncRecorder/CsvRecorder 保存。达到时长发送 STOP 后退出；检查序号缺失/重复/乱序、数值、板端时间、UART异常、CSV回读、未保存数量与端口收尾。60秒通过后，另用 `--seconds 600` 与新的输出目录测试10分钟。

工具只验收后端及 CSV，不冒称 GUI 或刷写验证；没有备份、烧录、恢复能力，也不会自行尝试进入 Bootloader。未知应答不会继续发送 PING 或 START。实际运行中的 CTRL-C 仍须检查报告与固件是否停止，不能将主机停止等同于设备 STOP 应答。

## 当前证据

- Windows 与 pySerial 只发现 CH340 COM8（1A86:7523、位置1-8.4.2）及四个蓝牙 COM。
- OpenOCD 的 CMSIS-DAP 后端实际返回 `unable to find a matching CMSIS-DAP device`；未确认 G431 身份，未备份、刷写、复位。
- 先前 COM8 在115200下被动监听10秒，仅一个 `00`，无有效采样，TX为零，不算通信通过。
- 新固件编译为9408字节；SHA-256 见生成的 manifest。尚未上板，不能据此宣称100Hz实板吞吐已达标。
- 接收诊断先取得6项失败证据。一次中间复跑为60通过/1失败，原因为测试把FireWater普通文本误当成错误；改用NaN输入并新增文本保留用例后，相关62项通过。夹具/诊断17项通过，验证了200帧分片解析、异步CSV往返和错误路径；离线结果不替代实板。
- 完整回归：802项通过，50.15秒，报告 `build-preview/runtime-g431-uart-20261027/regression.xml`。最终相关检查41项通过，8.30秒。普通测试未访问实板。
- 新软件 `dist/Astrspire-v0.6.0-dev3-uart-test.exe` 已构建，85,560,846字节，SHA-256 `DF413B4CF4933E25038D56DAF8C14B8E92D6194128007B5C3BA7AA88A9E2D561`；空工作目录下实际主窗启动、响应、正常退出通过，窗口标题沿用 dev3。旧版 EXE 哈希保持不变。该独立测试版不是已验证 G431 完整通信的发布版。
- 打包器提示未安装可选 `pyqtgraph.opengl` 的 `OpenGL` 包；本轮使用二维波形，不新增依赖，不宣称验证了三维 OpenGL。
- 最新串口枚举仍只有 CH340 COM8 和蓝牙端口。DAP枚举未成立前不盲刷、不冒充实板完成。源代码包和测试固件另行归档到 dist，原 dev3 包保留。

### 用户确认 COM8 后的实际 UART 检查

COM8 已由用户指定为 G431 实板串口，不再以串口名称不匹配阻止测试。在115200/8N1下，通过本应用接收线程监听10秒，仅1字节 `00`；随后通过同一应用的 TX 队列发送一次 `ASTR:HELLO\r\n`，12字节全部交付驱动，无错误，等待5秒仍只有 `00`，没有有效身份/文本或采样应答。主机停止、串口关闭及租约释放均正常。未发送 START、LED、ISP 或复位命令，未刷写。

报告在 `build-preview/runtime-g431-uart-20261027/com8-confirmed-rx-02.json` 和 `com8-hello-01.json`。不得将主机写入完成或 `00` 噪声当作成功往返。新测试固件已编译但未烧入；需进一步确认现有固件是否输出、UART接线及可用调试器，才能推进波形/持续采集。此段为源码包生成后的补充实测记录，不改写旧归档。
